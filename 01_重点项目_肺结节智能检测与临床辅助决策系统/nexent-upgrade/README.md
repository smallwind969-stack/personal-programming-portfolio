# 肺结节辅助复核系统：Nexent 升级工程

目标是把现有 PyTorch 检测/分类能力作为受控 MCP 工具接入 Nexent，同时保留医生的最终复核权。当前已落地的是**本机单人演示所需的安全接口切片**：病例清单、病例 ID 调用、候选编号、模型评分与医生确认状态分离。2026-10-07 已在本机 Nexent 的“我的 MCP”中注册带令牌的 HTTP 服务，平台联调显示“连接成功”“2 个工具”。后续空病例固定用例中，Qwen3 8B 曾触发一次可由服务端签名审计核验的真实 MCP 调用，并收到预期 404；但模型随后错误处理失败，还出现过伪造工具实现被平台自验证误判为通过。演示 Agent 保持草稿，真实病例推理、稳定降级与知识库审校仍待完成。

```text
脱敏演示病例清单 → 模型服务 /detect → 候选 ID + run_id
                                   ↘ /identify → model_score（待复核）
Nexent（MCP 已联通） → MCP 工具（仅病例/候选 ID） → 模型服务（待真实病例验证）
医生工作台 → 显式确认/驳回 → 才能进入最终复核结节列表
```

## 已实现与验证

- `model-server/`：FastAPI 接口只接受病例 ID；目录由服务端白名单解析，令牌保护推理接口；检测候选在服务端缓存供本次分类调用。
- `mcp-server/`：`stdio` 和带 Bearer 鉴权的 HTTP 两种入口，工具只暴露 `case_id`、`run_id`、`candidate_ids`；错误不回显服务响应体或本地路径。Nexent Docker 实例已通过 HTTP 完成发现和连通性校验。
- 组合工具 `analyze_case_candidates(case_id)`：在工具端串行检测与分类，检查同病例、同批次、同组候选 ID，输出仅含待复核评分的结果或固定失败说明。2026-10-09 通过独立 HTTP MCP 空病例烟测；Nexent Agent 尚未对该新工具完成对话验收。
- 组合工具在 Nexent 中已经刷新并独占绑定到草稿 Agent，但自然提问仍未触发工具；固定动作探针又重复调用 4 次。该 Agent 不得作为当前演示包的可信入口，具体证据见[联调记录](deploy/integration-log-2026-10-07.md)。
- `model-adapter/`：本机实验适配层，将 Nexent 的 OpenAI 聊天接口转至 Ollama 原生 `think=false`，避免 Qwen3 思考标记混入 CodeAgent 动作。固定动作探针已产生一次可验签的真实 MCP 调用，但自然语言请求没有稳定触发工具，真实工具错误后的最终回答也未通过独立降级门禁。
- 工具返回采用 `ok` 显式状态；失败只给错误码与说明，不附候选或批次。此改动针对真实联调中 Agent 把错误字符串当字典解析的故障，尚未证明 Nexent 最终回答已可靠。
- MCP 运行时还要求 `MCP_ALLOWED_CASE_IDS` 明确限定本次演示病例；模型编造其他 ID 时在工具层拒绝。可选签名审计和 `deploy/verify_mcp_trace.py` 用于证明真实工具处理函数被调用，审计不记录原始病例 ID。
- `deploy/verify_agent_failure.py` 把签名工具事件与空病例的最终回答一起检查；平台自检分数或代码文本不能替代真实调用。2026-10-08 Nexent 复验再次出现“输出代码但未执行工具”，因此 Agent 仍保持草稿。
- `../FJJ System/doctor_review.py`：模型候选默认未确认，只有医生明确确认且未驳回才进入最终结节。
- `../FJJ System/model_run_evidence.py` 与工作台：输入 `run_id` 后，服务端使用令牌核验当前病例的真实运行缓存；页面只读显示候选编号和评分。随访接口只读取服务端已保存的复核记录。旧页面的原有检测按钮仍属旧链路，不作为 Nexent 工具调用证据。
- `../FJJ System/agent/followup_agent.py`：无确认结节时返回“待复核/未评估”，不输出低风险判断。
- `knowledge-base/`：当前均视为待专家审核草稿，**暂不直接导入 Nexent**。
- 本机调试：通过实际 HTTP MCP 通道，未登记的 `demo-001` 返回工具错误/HTTP 404，未泄露病例路径。Qwen3 8B 经固定 `/no_think` 用例触发过一次真实工具调用；其后续推理仍不可靠。自验证也曾误判伪造工具实现为通过。完整对照见 [联调记录](deploy/integration-log-2026-10-07.md)。

## 本机启动顺序

1. 按 [模型服务说明](model-server/README.md)准备脱敏 DICOM、病例清单、服务令牌并启动模型服务。
2. 按 [MCP 说明](mcp-server/README.md)安装依赖并用相同令牌启动工具。
3. 按 [Nexent 接入清单](deploy/configure-agent.md)验证实际安装版本的模型、MCP 和知识库配置，保存真实运行证据。

若同时打开旧医生工作台 `FJJ System/app2.py` 核验批次，该进程也需设置相同的 `MODEL_SERVER_TOKEN`；`MODEL_SERVER_URL` 默认 `http://127.0.0.1:8100`。先在工作台选中与模型服务病例清单同名的脱敏病例，再把真实检测工具返回的 `run_id` 粘贴到“从模型服务核验”。核验失败不会生成候选或补造评分。

模型权重与性能数值沿用旧项目资料，但本切片的测试使用模拟推理引擎，**尚未验证实际影像推理效果或临床性能**。工具输出仅供辅助复核，不能替代医生诊断与管理决策。

工作台只读核验入口要求该病例先在旧工作台中存在，且模型服务病例清单使用相同的脱敏 `case_id`。运行缓存只在当前单进程有效；服务重启或该病例再次检测后，旧 `run_id` 将失效。模型服务 1 mm 重采样坐标与旧工作台预览图的切片映射尚未对真实病例逐一核对，因此核验结果不自动定位或写入医生复核记录。旧页面的模型候选仍由浏览器提交，尚不具备独立的来源证明；这一限制要在参赛材料和演示中如实说明。
